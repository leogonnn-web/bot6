### 0.1. Архитектурные факты (принять как данность, не перепроверять)

- **Спот, не фьючерсы.** Нет маржи, нет плеча, нет ликвидаций, нет Mark Price, нет funding.
  Риск = падение цены купленной монеты. «Голая позиция» = купленная монета без выставленного ордера на продажу.
- **Синхронный код на потоках, НЕ asyncio.** `asyncio` используется только внутри WS-листенера
  (`asyncio.run` в daemon-потоке, `src/api/bybit_client.py:310-315`). Основной цикл — синхронный `while`.
  Следовательно: `asyncio.Lock` здесь **неприменим**, правильный примитив — `threading.Lock`/`RLock`.
- **Три потока делят состояние:** (1) основной цикл-стейт-машина, (2) WS-листенер, (3) background-сканер
  (`@BG_SCAN_THREAD@`, стартует в `src/core/bot.py`).
- **Стейт-машина:** `IDLE → SCANNING → BUYING → IN_POSITION → EXITING`, enum в `src/core/state_enum.py`,
  логика по состояниям — миксины в `src/core/states/`.
- **Ордера на выход — это лимитный sell (TP) + market sell (panic).** «Stop Loss» как биржевой ордер
  не используется: стоп реализован **программно** (`panic_stop`, проверка в `in_position.py`).
  Это значит: если процесс мёртв — стопа нет вообще. Учесть в §5 и §6.

### 0.2. Переформулировка вопросов под спот

Три из шести пунктов постановки сформулированы под фьючерсы. Отвечать на **спотовый аналог**:

| В постановке | Читать как |
|---|---|
| `asyncio.Lock` в критических методах | `threading.Lock` — гонки между main / WS / bg-scanner |
| «нехватка маржи» при выставлении стопа | `Insufficient balance` из-за комиссии 0.1% в базовой валюте |
| Mark Price vs Last Price, расчёт ликвидации | По какой цене срабатывает программный `panic_stop`: `last` / `bid` / `ask`, из WS-кеша или REST, и насколько эта цена свежая/синтетическая |
| «позиция останется голой» | Монета куплена, но ордера на продажу нет (`order_id=None`) |

Если по ходу аудита пункт постановки окажется физически неприменим — **так и написать**, с объяснением,
и разобрать спотовый аналог. Не изобретать фьючерсную семантику там, где её нет.

## 1. Формат отчёта

Каждая находка — строго в 4 полях:

```
### F-<NN> <краткое имя>

**Узел:** <файл:строки> — <функция/класс>
**Уязвимость в коде:** <что именно не так, с цитатой кода>
**Сценарий краха:** <пошаговый сценарий: шаг 1 → шаг 2 → ... → денежный итог>
**Конкретное решение:** <патч-диф или готовый блок кода>
```

Плюс обязательные поля для приоритизации:

```
**Severity:** CRITICAL / HIGH / MEDIUM / LOW
**Статус:** ПОДТВЕРЖДЕНО (прочитан код, строки указаны) / ГИПОТЕЗА (нужна проверка)
**Стоимость ошибки:** деньги / залипший стейт / бан ключа / шум в логах
```

### Правила достоверности (жёстко)

1. **Каждое утверждение о коде — со ссылкой `файл:строка`.** Не помнишь — открой файл.
2. **Не выдумывай функции, параметры и поля.** Если предполагаешь — ставь `Статус: ГИПОТЕЗА`.
3. **Сервер недоступен** (`ssh 54.179.1.197` таймаутит на 2026-09-05). Проверки в рантайме невозможны.
   Аудит **только по коду**. Не предлагать «посмотреть логи на сервере» как способ доказательства.
4. **Ничего не запускать в реальном режиме.** Никаких live-ордеров.
5. **Не править код в процессе аудита.** Решения — как патчи в отчёте. Применение — отдельным заходом
   по решению пользователя.
6. Severity ставить по **деньгам**, а не по элегантности кода.

### B7 — Атомарность «вход → защита выхода»

- Тот же разбор для grid-ветки: `hydra_net.py:_update_take_profit_for_grid` — там `except` только
  логирует `@TP_ERROR@` (`:305-306`), состояние не помечается как «без защиты». Проверить.
- `hydra_net.py:346-352` — если `order_cost < min_cost`, TP **не выставляется** и состояние
  сбрасывается в `IDLE` при, возможно, купленной монете. Проверить, это ровно тот класс баги,
  что чинили в июне, но в другой ветке.

### B8 — Kill Switch / Safe Mode

- Есть ли глобальный предохранитель? Разобрать `risk/safety.py`, `risk/limits.py`,
  `circuit_breaker` (в конфиге: `max_panics: 6`, `max_loss_usd: 3.0`, `window_sec: 600`),
  `stop_loss_total: 12.0`, `maintenance_mode`, `_check_global_safety`.
- Для каждого предохранителя: что он **фактически** останавливает — только новые входы,
  или и управление открытой позицией тоже? Если бот «замораживается» с открытой позицией и без
  TP-ордера — это не safe mode, а ловушка. Проверить.
- Есть ли путь «отменить все ордера → закрыть позиции → `sys.exit`»? Если нет — спроектировать,
  но с ответом на вопрос заказчика: **не зациклится ли аварийный выход, если API биржи лежит?**
  В решении обязательно: ограниченное число попыток, общий дедлайн (wall-clock budget),
  и **персист состояния на диск перед выходом**, чтобы после рестарта бот знал про незащищённую позицию.
- Учесть внешний контур: `restart: unless-stopped` в compose + watchdog. `sys.exit` приведёт
  к **автоподъёму контейнера**. Значит kill switch обязан оставлять на диске флаг, который после
  рестарта не даёт торговать (аналог `watchdog.pause`, но для бота). Проверить, есть ли такой флаг.
  Это важная связка — не пропустить.

### B9 — Корректность цен для программного стопа

Спотовая версия вопроса про Mark vs Last Price.

- Найти, по какой цене принимается решение о `panic_stop` в `in_position.py`: `last`, `bid` или `ask`,
  и откуда она берётся — из `ws_tickers_cache` или из REST.
- **Засеянная зацепка:** `bybit_client.py:79-105`, `_update_price`. Если Bybit не прислал
  `bid1Price`/`ask1Price`, код **синтезирует** их из `lastPrice` как `±0.05%` (`:86-91`).
  То есть решение о стопе может приниматься по **выдуманному спреду**, а не по реальному стакану.
  Оценить: на сколько это расходится с реальностью на тонких парах и к какой ошибке в PnL ведёт.
- Асимметрия: продаём мы в **bid**, а если `drop` считается от `ask` (в `scanning.py` берётся
  `tickers[symbol]['ask']`) — есть систематический сдвиг на величину спреда. При `spread_max: 0.25%`
  и TP `0.8–1.5%` это до трети ожидаемой прибыли. Проверить и посчитать.
- Свежесть: сопоставить с B3 — используется ли `is_data_fresh` перед расчётом стопа.
  Стоп по цене 30-секундной давности на падающем рынке = пропущенный стоп.
- Отдельно зафиксировать: **биржевого стоп-ордера нет**, стоп существует только пока жив процесс.
  Явно указать это как архитектурный риск с оценкой: что будет, если контейнер упадёт с открытой позицией.
