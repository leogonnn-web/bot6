# HYDRA (bot4-main) — комплексный технический аудит

Дата: 2026-09-06. Режим: только чтение, код не менялся.
Охват: Python-бот (`main.py`, `shared/`, `src/`), Go-движки (`go-scalper/`, `arb-engine/`), Docker/Terraform/monitoring, тесты, docs.
Все ссылки `file:line` сверены по файлам в рабочем дереве (включая незакоммиченные правки из HANDOFF).
Тесты: `python -m pytest -q` → 134 passed.

Легенда серьёзности: **C** — потеря денег / неуправляемая позиция; **H** — высокий риск сбоя или безопасности; **M** — дефект/долг; **L** — мелочь.

---

## 0. Резюме (что важно понять за минуту)

1. **Все критические баги — одного класса:** бот принимает решение «позиции нет → IDLE» или «ордер исполнен» на основании *выдуманных* данных (заглушки при ошибках API), а не факта с биржи. Это ровно то, о чём совет «сравнивай два независимых источника одной величины». Реальный пилот (HANDOFF §4: баланс $22 → $4.7 из-за непроданных покупок) — прямое следствие.
2. **Live-режим сетки (grid, max_levels > 1) сломан логически**, но это не видно в dry-run: `_update_take_profit_for_grid` отменяет только что созданное колено покупки (C2). Все прогоны были dry-run → баг никогда не проявлялся.
3. **Безопасность:** секретов в коде нет, `.env` не трекается — хорошо. Но `POST /maintenance` (принудительное закрытие позиции) **без аутентификации на порту 9090, открытом в Security Group на 0.0.0.0/0**. Grafana с дефолтным паролем тоже открыта миру.
4. **Watchdog/health имеют ложные срабатывания**: порог 15 с при scrape 10 с и `sleep(5)` в IDLE → рестарты «здорового» бота с SIGKILL через 2 с.
5. Много мёртвого/дублирующего кода (второе определение `_handle_scanning_state`, `_fix_executed_grid_deal` с NameError, `shared/database.py`, `shared/exchange_utils.py`, ~50 `tmp_*.py` в корне, 25 МБ логов и .exe в git).

## 1. CRITICAL — риск потери денег / неуправляемой позиции

### C1. `fetch_order` после 3 неудач возвращает выдуманный ордер `{'status':'closed','filled':0.0}`
`src/api/bybit_client.py:552-570`. Три подряд ошибки API (~1.5 с при 429/сетевом сбое) превращаются в «ордер исполнен на 0».
Последствия по вызывающим:
- `src/core/states/buying.py:228-241` → `filled=0.0, avg_price=0.0` → `_on_buy_filled(symbol, 0.0, 0.0)` → `target_sell_price = 0` (buying.py:57), TP-ордер по цене 0 отклоняется биржей → IN_POSITION с `buy_price=0`.
- `src/core/states/in_position.py:33` → `ZeroDivisionError` каждую секунду, ловится в `:188-189` → бот **вечно застревает** в IN_POSITION без выхода.
- `src/core/states/in_position.py:149,164-170` → у фейкового ордера нет `side` → ветка `@NO_TP_ORDER@` → `_panic_sell()` → **отменяет реальный TP и продаёт позицию по рынку** из-за сетевой икоты.
- `src/core/states/exiting.py:43-49` → фейковый «closed» с `price=None` → `close_price=0` → в БД записывается продажа по 0 (PnL = −buy×amount), состояние → IDLE, монета может остаться на балансе.
- `src/core/grid/hydra_net.py:87-91` → `_on_grid_level_filled` (там защита `:180-182` отбивает нули — единственное место, где это безопасно).
Тот же паттерн в мёртвом `shared/exchange_utils.py:213-214`.

### C2. Live-сетка: `_update_take_profit_for_grid` отменяет только что созданное колено покупки
`src/core/grid/hydra_net.py:236-247` — создаётся buy-ордер следующего колена, `state_data['order_id'] = <buy_id>`, затем сразу вызывается `_update_take_profit_for_grid`, который в `:276-282` отменяет `state_data['order_id']` (то есть **этот же buy**) и записывает в `order_id` id TP-sell-ордера (`:302`).
Дальше цепочка:
- бот остаётся в BUYING; `buying.py:228-239` опрашивает `order_id` = TP-sell; когда TP исполняется — это трактуется как **исполнение колена покупки** → `total_cost/total_qty` растут на проданное количество (hydra_net.py:185-186).
- `_synchronize_grid_network` (hydra_net.py:138-143) делает `amend_order` на sell-ордер с захардкоженным `side='buy'` (`bybit_client.py:527`).
- `buy_time` не обновляется при заполнении колена (hydra_net.py:241-244), поэтому через `order_execution_timeout_sec=60` в BUYING срабатывает `buying.py:246-272`: либо `fetch_my_trades` находит покупку последних 60 с и **учитывает её второй раз** (`:250-258`), либо отменяет TP-sell и уходит в IDLE **с монетами на балансе**.
В dry-run баг замаскирован: для `virtual_*` id отмена пропускается (hydra_net.py:277).

### C3. Сброс в IDLE при удерживаемой монете (осиротевшие позиции)
`IDLE` = «позиции нет», но в этих местах в IDLE уходят без проверки баланса базовой монеты:
- `src/core/grid/hydra_net.py:265-268` — любое исключение в `_on_grid_level_filled`, включая падение `order_manager.buy` на `:236` (`Insufficient balance` на мартингейл-размере) → IDLE, а монеты с уже заполненных колен остаются.
- `src/core/states/buying.py:242-245` — `status == 'canceled'` без учёта частичного исполнения.
- `src/core/states/buying.py:265-272` — таймаут: отмена ордера без чтения `order['filled']`; `fetch_my_trades` в `:250-258` берёт **один последний трейд** (`buy_trades[-1]`), а не сумму — частичные исполнения нескольких трейдов недоучитываются.
- `src/core/states/buying.py:277-278, 281-282`.
- `src/core/states/exiting.py:50-53` (exit canceled), `:76-78`, `:81-82`, `:115-118`.
- `src/core/states/exiting.py:176-179` — если market backstop падает, `exit_order_id` остаётся id отменённого лимитника → следующий тик `:50-53` → IDLE.
- `src/core/states/in_position.py:429-433` (maintenance).
- `src/core/states/in_position.py:114-128` — «нулевой баланс» из заглушки (см. C4) → `@RESET@` → IDLE.
Нужен единственный выход в IDLE через функцию, которая сверяется с биржей (см. план, П1).

### C4. Заглушка `fetch_balance` делает инварианты fail-open
`src/api/bybit_client.py:433-439` — в live при ошибке возвращается `{'free': {'USDT': 0.0}, 'total': {...}}` **без `info.result.list[0].coin[]`**. Все места, парсящие UTA-структуру, при ошибке видят «монет нет»:
- `src/core/states/buying.py:150-165` — Single Position Invariant: `uta_coins=[]` → блокировки нет → **покупка разрешена** (плюс `:164-165` явно «Proceeding with caution» при исключении). Подтверждён риск из ТЗ.
- `src/core/states/in_position.py:107-128` — две подряд неудачи `fetch_balance` (1 с) → «Safe reset» → IDLE при живой позиции и открытом TP.
- `src/core/bot.py:313-317` — `_recover_from_exchange` читает `bal.get(base, {}).get('free')` → 0 → `@RECOVER_GHOST@` → IDLE при рестарте, если API моргнул.
- `src/core/states/buying.py:88-102` — fallback продаёт `amount*(1-0.0015)`; если реальная комиссия/дастинг больше — `170131 Insufficient balance` и TP не встаёт.
Дополнительно: поле `equity` захардкожено под UTA. На классическом spot-аккаунте структура другая → баланс всегда 0 → бот будет «сбрасываться» постоянно. Никогда не проверялось, какой тип аккаунта на ключах.

### C5. Таймаут выхода = «считаем, что продали»
`src/core/states/exiting.py:54-73` — через 60 с без подтверждения бот записывает в БД продажу по fallback-цене (`bid` или `buy_price*0.98`) и уходит в IDLE, **даже если ордер не исполнен** (например, отклонён или лимит-чейз не дошёл). Позиция теряется из state, `trades.db` содержит фиктивную сделку, риск-лимиты и Grafana видят несуществующий PnL.

### C6. Цена 0 или устаревшая цена запускает стоп
- `src/core/states/in_position.py:26` — если символа нет в `ws_tickers_cache`, берётся `fetch_ticker()['last']`, который при ошибке = `0.0` (`bybit_client.py:449-455`) → `change_percent = -100%` → `is_sl_hit` → `_panic_sell(urgent=True)` → **маркет-продажа по сетевой ошибке**.
- В `in_position.py` нет проверки свежести `ws_data['timestamp']`; записи в `ws_tickers_cache` никогда не вытесняются (`bot.py:605`), поэтому после отвала WS (см. H6) стоп/TP считаются по замороженной цене неопределённо долго. Это и есть вопрос ТЗ «по какой цене срабатывает программный panic_stop».

## 2. HIGH

### H1. [Security] Неаутентифицированный `POST /maintenance` открыт в интернет
- `shared/metrics.py:139` — `HTTPServer(('', port))` слушает все интерфейсы; `:184-193` — `POST /maintenance` вызывает `bot.enter_maintenance_mode()` без токена/проверки источника.
- `docker-compose.yml:20-21` — `9090:9090` наружу; `terraform/main.tf:76-79` — SG разрешает 9090 с `0.0.0.0/0`.
Любой сканер интернета может форсировать закрытие позиции (по лимиту за 300 с, потом маркет). Также `GET /maintenance` раскрывает состояние и символ позиции.
- Grafana: `docker-compose.yml:91` пароль по умолчанию `triada2024`, порт 3000 открыт миру (`main.tf:67-70`). Prometheus UI 9092 тоже открыт (`main.tf:94-97`).
- `HTTPServer` однопоточный (`metrics.py:139`) — один медленный клиент блокирует scrape → watchdog видит «пропажу метрик».
- `start_server` глушит `OSError` (`metrics.py:141-142`) — при занятом порту бот работает без метрик молча.

### H2. Watchdog: ложные рестарты с SIGKILL
- `docker-compose.yml:116` `STALL_THRESHOLD_SEC=15`, `monitoring/prometheus.yml:2` `scrape_interval: 10s`. Значение `hydra_heartbeat_timestamp` в Prometheus отстаёт от реального до 10 с даже у здорового бота.
- Главный цикл блокируется: `src/core/states/idle.py:26` `sleep(5)` при неудачной проверке (низкий баланс — постоянное состояние в пилоте), `bot.py:537` `sleep(1)`, `bot.py:540` `sleep(10)` при ошибке, `hydra_net.py:318` `sleep(2.5)`, плюс REST-вызовы ccxt с таймаутом 10 с. 10 + 6 > 15 → `heartbeat_stalled` (`watchdog.py:240-243`).
- `restart(timeout=2)` (`watchdog.py:278-280`, `RESTART_TIMEOUT_SEC=2`) → SIGTERM и через 2 с SIGKILL, пока бот может быть внутри создания ордера. `_signal_handler` сохраняет state (`bot.py:232-235`), но `state_data` пишется на диск только при смене состояния (`bot.py:492-495`) — id ордеров сетки, `partial_tp_hit` и т.п. между сменами состояний не персистятся → после рестарта восстанавливается **устаревший `order_id`**.
- `watchdog.py:277-283` — при ошибке `restart` `last_restart_ts` не обновляется → плотный цикл попыток каждые 5 с.

### H3. HealthChecker: мёртвая проверка и самоубийственный SIGTERM
- `src/core/health.py:134` — `state in ['IN_POSITION', 'BUYING', 'EXITING']` сравнивает `BotState` (Enum, `state_enum.py:5`) со строками → **всегда False**, проверка «застрял» никогда не срабатывает. Тест проходит, потому что подставляет строки (`tests/test_health.py:83,91`) — классическое расхождение теста и продакшена.
- `health.py:111-113` требует ≥95% тикеров свежее 10 с. В конфиге 130 символов (`shared/config.json:54-185`), многие неликвидны/не существуют на Bybit; в live 5% = 6 символов без апдейта 10 с → 3 провала × 30 с → `os.kill(SIGTERM)` (`health.py:160-167`) → рестарт-цикл. В локальном логе 23 `@HEALTH_CRITICAL@` (частично от тестов, но паттерн `['exchange_api','tickers_cache']` — реальный).

### H4. Ретрай-штормы без backoff и REST-нагрузка в IN_POSITION
- `in_position.py:296-300` — при падении `_panic_sell` состояние не меняется и попытка повторяется **каждую секунду** (cancel + fetch_balance + order) без лимита/алерта. Нет `halt after N failures` (совет №2 из другого проекта — актуален именно здесь).
- Каждую секунду в live IN_POSITION: `fetch_balance` (`in_position.py:107`), `fetch_order` (`:136`), `fetch_ohlcv` через `_calculate_adaptive_breakeven_timeout` (`:177` → `breakeven.py:72`). Это ~3 REST/с → 429 → падает `fetch_order` → включается C1.
- `_launch_grid_network` проверяет только конфиг-минимум (`hydra_net.py:437-440`), не `markets[symbol]['limits']` (min amount / min cost / lot step). При `slot_size=3.0` округление `amount_to_precision` вниз легко даёт ордер ниже минимального нотионала Bybit (обычно 1–5 USDT по паре) → reject → исключение → IDLE. Совет №4 (квантизация по спекам) — в точку.

### H5. Асимметрия ретраев и захардкоженный side
- `bybit_client.py:473-498` — создание ордеров без ретрая (только `raise`), но `amend_order` ретраит (`:509-550`). Обратная логика: ретраить безопасно можно **только** идемпотентно (clientOrderId), иначе двойной ордер; сейчас же `raise` из buy в `_on_grid_level_filled` → C3.
- `bybit_client.py:527` `side='buy'` в `amend_order`, но он используется для **sell**-чейза (`exiting.py:189`).

### H6. WebSocket: смерть навсегда и синтетические цены
- `bybit_client.py:301-304` — после 10 реконнектов `ws_running=False`, поток умирает, процесс живёт на REST раз в 5 с (`bot.py:626`). Никакого алерта/рестарта WS.
- `bybit_client.py:226-232` — таймаут ack подписки игнорируется; неподписанные символы тихо не получают цен.
- `bybit_client.py:86-91` — bid/ask синтезируются как `last ± 0.05%`. Bybit V5 spot `tickers` **не присылает** bid/ask в дельта-апдейтах, значит почти всегда спред «0.1%»: фильтр `spread_max` (`scanning.py:398-401`) неинформативен, лимит-чейз выставляется по выдуманному ask (`in_position.py:236,251`).
- `bybit_client.py:358-361` — `is_active()` итерирует `last_update_time.values()` без `update_lock` → возможен `RuntimeError: dictionary changed size` из WS-потока.

### H7. Учёт PnL ведётся двумя несогласованными способами
- В памяти: `session_profit += _calc_pnl(...)` с комиссиями (`bot.py:744-754`).
- В БД: `get_session_stats` считает **брутто** `(price - buy_price) * matched` (`src/database/models.py:226`), колонка `profit` игнорируется, `sell_partial` не считается (`:212-221`).
- Риск-лок капитала использует брутто из БД (`src/core/risk/limits.py:57-58`) → убытки занижены на комиссии.
- Частичный TP записывает прибыль **до исполнения** лимитного ордера (`in_position.py:326-336`).
- `_on_exit_filled` считает PnL по `exit_amount`, а не по фактически исполненному (`exiting.py:97`).
- `bot.py:101-102` восстанавливает `session_profit` из БД, а `_load_state` `:277-280` его обнуляет — два источника одного числа.
- `get_daily_trades_count` (`models.py:271-273`) считает строки таблицы (buy + sell + sell_partial + buy_grid_complete) — `max_trades_per_day` ограничивает «ноги», а не сделки.
Ровно тот случай «число, которое считается двумя способами и ни разу не сверялось».

### H8. «Безубыток» — не безубыток
`src/core/risk/breakeven.py:29-46` — вычисленный `breakeven_multiplier = 1 + taker + maker + 0.0002` перезаписывается `buy_price * 1.001` (`:44`). При 0.1% на каждую ногу «безубыточный» выход фиксирует ≈ −0.1%. Мёртвый код `:41-42`.

### H9. Потокобезопасность (фоновый сканер ↔ главный цикл)
Фоновый поток `_background_scan_loop` (`bot.py:712-739`) и main без общих локов трогают: `self.price_history` (`scanning.py:424-431` vs `hydra_net.py:495`), `self.ws_tickers_cache` (чтение vs запись `bot.py:605`), `symbol_manager`/`ScannerIntegration` (`scanner.py:38-70, 99-119`), кэш индикаторов `IndicatorWrapper._cache` (`src/indicators/matrix.py:731-795`) и глобальный `analyzer` (`:988-1017`), `toxic_filter` (внутри есть лок). `sqlite3` открыт с `check_same_thread=False` (`models.py:32`) и не защищён — пока в фоне БД не пишут, но ограждения нет.

### H10. Go-scalper (не в compose, но собран и «живой»)
- `go-scalper/internal/exchange/rest.go:49-75` — подпись HMAC считается только от `body`; для GET (`GetOrder`, `GetWalletBalance`, `:139-177`) query-string не подписывается → аутентификация V5 не пройдёт.
- `rest.go:16-17` учитывает `testnet`, а `ws.go`/`private_ws.go:19` захардкожены на `stream.bybit.com` (mainnet) → смесь testnet REST и mainnet данных.
- `orders.go:81/106, 302/323` — `defer ActiveSlots.Dec()` до `Inc()` → отрицательный gauge; `orders.go:97,131,151,208,256,477` — цены/кол-во форматируются фиксированными 4/8 знаками без lotSizeFilter; гонки на `SymbolData` ring-буферах (`engine/state.go:48-89`, `strategy/matrix.go:97-106`), underflow `(SecHead-1)%SecCap` при `SecHead==0`; утечка heartbeat-горутин при каждом реконнекте (`ws.go:115`, `private_ws.go:145`); `ratelimit.go` не подключён (`rest.go:29-39`).
- Реальные ордера ставятся при `dry_run:false` (`main.go:59-87`), других предохранителей нет.
`arb-engine` — только логирует возможности, ордеров не ставит (`arb-engine/cmd/arb/main.go:137-156`); утечки ping-горутин и реконнект без backoff (`bybit_ws.go:47-95`, `bitget_ws.go:35-86`).

## 7. Оценка рекомендаций от других ИИ

**Советы из triada-futures (5 пунктов):**
- №1 (проверка целостности книги) — **самый ценный**, напрямую закрывает C3/C4/C5. Реализовать как п.9 плана.
- №2 (планировщик с состоянием, halt после N неудач) — DCA-часть не про Hydra, но `halt after N consecutive failures` нужен для `_panic_sell`/exit (H4, п.10).
- №3 (файловый лок) — актуален: один `.env` и один код на локальной машине и на сервере; двойной запуск = двойная позиция при отсутствующем Single-Position-инварианте (C4). п.20.
- №4 (квантизация по спекам) — актуален: `slot_size=3.0` и отсутствие проверки `limits` (H4/п.14). Про «ETHUSDT общий id спота и перпа» — в ccxt `defaultType: 'spot'` задан (`bybit_client.py:383`), в Go-скалпере `category` явно `spot` — риск ниже, но `verify_keys.py` не проверяет тип аккаунта.
- №5 (append-only журнал) — да, п.22; и главный тезис «сравнивать два источника» — это буквально диагноз данного кода (H7, C1–C6).
- Не переносить: vol targeting, плечо, фандинг — согласен.

**ТЗ `docs/AUDIT_TZ_RESILIENCE.md`:** все шесть зацепок подтверждены построчно (`bybit_client.py:552-570, 473-498, 86-91, 301-304, 227-232`, `hydra_net.py:346-352`).
